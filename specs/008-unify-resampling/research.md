# Phase 0 Research: Unify label-aware resampling

## Decision: rename `upsample`'s `--smooth <sigma>` to `--label` (boolean, fixed internal sigma)

**Decision**: `upsample`'s existing optional `--smooth <sigma>` (float) becomes `--label` (a boolean flag, no value) — matching `downsample`'s new flag exactly in name and framing ("treat as label/segmentation data"). Presence of `--label` triggers the same underlying softening step (`_smooth_labels`, per-label-channel Gaussian blur + argmax re-snap) `--smooth` always triggered, but using a fixed internal sigma constant (`_LABEL_SMOOTH_SIGMA`, chosen as `1.0` — a simple, reasonable one-voxel-scale default) instead of a caller-supplied value.

**Correction**: this was originally assumed to already exist ("`upsample --label`, pre-existing, out of scope") when this plan was first drafted. It doesn't in the actual repository baseline — a prior, unrelated exploratory rename to `--label` had been made and then explicitly reverted (along with other uncommitted work) before this feature's `/speckit-specify` run even started, and that revert wasn't accounted for when spec.md/plan.md were first written. Discovered mid-implementation (while writing a TUI test against `upsample`'s actual current form fields, which still showed `#field-smooth`, not `#field-label`). Fixed by updating spec.md/plan.md/data-model.md/contracts/ to correctly scope this rename as part of User Story 2, and adding real implementation tasks for it to tasks.md.

**Rationale for dropping CLI-tunable sigma**: `downsample`'s and `apply_mask`'s label-safety flags/behavior are both plain booleans (no tunable parameter) — matching that shape keeps the three commands' "treat as label data" switch uniform. `upsample`'s default (exact nearest-neighbor repeat) is already label-safe regardless of this flag; `--smooth`/`--label` was always an optional cosmetic refinement (softening blocky upsampled edges), never a correctness requirement, so losing fine-grained sigma control is a real but low-stakes UX simplification, not a safety regression.

**Alternatives considered**: keep `--smooth <sigma>` as a second, optional companion flag alongside a new boolean `--label` (requiring both, or `--label` implying a default sigma while `--smooth` overrides it) — rejected as unnecessary complexity for a purely cosmetic knob; a single boolean matches the other two commands' flags exactly and is simpler to document/remember.

## Decision: two shared primitives in `core/resample.py`, both lazy via `dask.array.map_blocks`

**Decision**: `intensity_downsample(data: da.Array, factor=2, *, downsample_func=skimage.transform.pyramid_gaussian) -> da.Array` and `label_downsample(data: da.Array, factor=2, *, smooth=None, downsample_func=...) -> da.Array` both take and return **lazy** dask arrays. Each dask block is resampled independently inside a `map_blocks`-wrapped closure — the array is never materialized in memory all at once, only one chunk at a time ever is.

**Rationale**: explicit user requirement ("always prioritize lazy loading... have dask's map_block run on chunks, calling this function downsample_func"). An earlier draft of this design had both functions operate eagerly on materialized `numpy.ndarray`s (justified at the time by precedent: `upsample --smooth`'s existing `_smooth_labels` already materializes). That eager version was rejected in favor of the lazy one specifically to avoid a real regression for `from_images` on large (organ-scale) volumes, where materializing a full level into memory just to downsample it would be a meaningful loss of out-of-core scalability versus the previous `bioio_ome_zarr`-based writer (which resized chunk-wise via `dask.array.map_blocks` internally, staying lazy).

**Verified empirically**:
- `skimage.transform.pyramid_gaussian`'s actual output-shape rounding convention is **ceiling** division (`math.ceil(size / downscale)`), not floor — confirmed for shape `17` → `9` (not `8`). This must be declared correctly as `map_blocks`'s `chunks=` argument (via a small helper, `_downsampled_chunks`) or dask raises a shape-mismatch error at compute time.
- Per-block ceiling-division sizes compose correctly with dask's own chunking even for non-uniform/boundary chunks (a size-17 array chunked `(8, 8, 1)` downsamples per-block to `(4, 4, 1)`, summing to `9` — matching the whole-array reference exactly for this codebase's actual chunking patterns, which always use a fixed nominal chunk size per axis with only the trailing boundary chunk potentially uneven).
- Chaining two `map_blocks`-wrapped calls (building level 2 from level 1's lazy output) stays lazy and composes correctly; `.compute()` on the result matches its lazily-declared `.shape`.

**Alternatives considered**:
- *Eager (materialize-then-compute) primitives* — rejected per the explicit lazy-first instruction above; also would have required `apply_mask` to keep manually `.compute()`-then-rewrap its mask array (as it originally did), which the lazy design eliminates entirely (a nice simplification, not just a tradeoff avoidance).
- *`dask.array.map_overlap` (with a halo/margin between chunks)* — would avoid the minor cross-chunk-boundary blending-precision loss that per-block-independent Gaussian smoothing has (each chunk's edge is smoothed using only that chunk's own `reflect`-padded data, not real neighboring-chunk data), but adds real complexity (picking an overlap depth from `sigma`). Rejected: the *previous* `bioio_ome_zarr`-based writer already made the exact same chunk-local-no-overlap tradeoff for its own (nearest-neighbor) resizing, so this isn't a new precision loss being introduced, just the same one carried over to an antialiased method — not worth the added complexity for a precision difference this codebase has never had a problem with.

## Decision: `label_downsample`'s per-channel label decomposition is chunk-local, not global

**Decision**: `np.unique(block)` runs on each dask block independently inside the `map_blocks` closure, not once globally (`da.unique(data).compute()`) before dispatching.

**Rationale**: a block-local subset of the dataset's full label set is sufficient to preserve the "never invent a new value" guarantee — every output voxel still ends up as one of the labels present in its own local neighborhood, which is necessarily a subset of the global label set too. Computing global unique labels first would require an extra full-array pass (itself against the lazy-first goal) for no correctness benefit.

**Alternatives considered**: global `da.unique(data).compute()` first, then pass the fixed label set into every block — rejected as an unnecessary eager pre-pass; no test or requirement needs consistent channel *ordering* across blocks (each block's own `argmax` re-snap is independent of any other block's).

## Decision: `write_new_pyramid` derives each level's shape *and* scale metadata from the same real downsample output (bug found and fixed during design)

**Decision**: `core/pyramid.py::write_new_pyramid` takes `num_downsampling: int`, not a precomputed `level_shapes: list[tuple[int, ...]]`. Each level's array shape (used for `zarr.Group.create_array(shape=...)`) and its `coordinateTransformations[0].scale` metadata are *both* read from the same lazily-declared `.shape` of that level's actual `intensity_downsample(...)` output — never from an independently computed value.

**Rationale**: An earlier draft reused this codebase's existing `_level_shapes()` helper (`max(1, s // 2)` floor-based halving, precomputed ahead of time) to size the array, while still deriving scale from `intensity_downsample`'s real output — a split source of truth. Verified empirically that these two values only coincide for even-sized dimensions (which is every dimension in this repo's existing test fixtures); for a real-world odd dimension (e.g. `17`), `skimage`'s actual ceiling-based output is `9` while the floor-based precomputed value is `8` — the buggy design would have written a real `9`-sized array but recorded a scale value computed against a `8`-sized denominator that doesn't exist on disk (`2.0 * 17/8 = 4.25` instead of the correct `2.0 * 17/9 = 3.777...`, confirmed by direct computation). Deriving both from the one real value eliminates the divergence by construction. This also let `from_images.py` drop its `_level_shapes()` helper entirely (confirmed unused elsewhere in the codebase via `grep`).

**Alternatives considered**: keep `_level_shapes()` and add a runtime assertion that the real output matches the precomputed value, raising a clear error on mismatch instead of silently writing wrong metadata — rejected as strictly worse than just not having two sources of truth in the first place; the fix costs nothing extra.

## Decision: batch every pyramid level's `da.store()` into one combined call per command invocation

**Decision**: both `core/pyramid.py::write_new_pyramid` (new) and `core/pyramid.py::commit_new_levels` (existing, shared by `downsample`/`upsample`) collect every level's `(source, target)` pair first, then issue **one** `da.store(sources, targets)` call across all of them, rather than one `da.store()` call per level in a loop.

**Rationale**: when levels chain lazily (level *N* is built by downsampling level *N-1*'s own lazy expression, as both `downsample --num_levels N>1` and `from_images --num_downsampling N>1` do), storing them with **separate** `da.store()` calls forces dask to recompute every shared upstream step once per level, since dask does not cache/dedupe work across *separate* `.compute()`-triggering calls on its own. Verified empirically with an instrumented "count how many times the raw source is read" test: three separate `da.store()` calls (one per level) read the shared upstream source **3 times**; one combined `da.store(sources, targets)` call reads it **once** and reuses it for every dependent level, because dask's scheduler recognizes and shares the common sub-graph within a single `compute()` pass.

`commit_new_levels` needed the same fix even though it wasn't originally in scope, because making `downsample.py`'s builder lazy (per the decision above) feeds directly into `commit_new_levels`'s existing per-level loop — leaving that loop unbatched would have introduced the exact same redundant-recomputation regression there, for the common case of `downsample --num_levels 2` or more.

**Alternatives considered**: leave `commit_new_levels` unbatched (one `da.store()` per level, as before) and accept the recomputation cost for `downsample`/`upsample` specifically — rejected: the fix is small, low-risk (preserves `commit_new_levels`'s existing collision-retry-then-store control flow exactly, just moves the actual `da.store()` call to after the loop instead of inside it), and avoids introducing a real, easily-observed performance regression as an unintended side effect of an unrelated feature.

## Decision: `write_new_pyramid` writes bare-bones metadata only (no translation, no `"omero"` block); explicit Blosc/zstd compressor preserved

**Decision**: `write_new_pyramid` writes exactly `{"scale": [...]}` per dataset — no `"translation"` transform, no `"omero"` metadata block. `from_images.py` keeps its own existing, separate post-processing step (`add_half_pixel_translations` + `write_multiscales`, both from `io/ome_metadata.py`, unchanged) to add translations afterward.

**Rationale**: verified empirically (dumping real `bioio_ome_zarr`-written attrs as JSON) that the previous writer's `"omero"` block is written unconditionally, even for a pure z/y/x volume with no channel axis, and that **no test in this suite** asserts on it (`grep -rn "omero" tests/` → zero hits) — safe to drop. Verified separately that `tests/conftest.py`'s own (pre-existing, separate) use of the same writer does **not** currently add translations to its fixture datasets (only a single `"scale"` transform per dataset) — folding `add_half_pixel_translations` directly into the new shared `write_new_pyramid` would have silently added translation metadata to every one of the ~19 test files that build on those fixtures, a wide, unintended blast radius. Keeping translation-adding as `from_images.py`'s own separate, explicit step (as it already is today) avoids this entirely.

Also verified: the previous writer explicitly set a `Blosc(cname="zstd", clevel=3, shuffle=BITSHUFFLE)` (Zarr v2) / `BloscCodec(cname="zstd", clevel=3, shuffle="bitshuffle")` (Zarr v3) compressor rather than relying on `zarr`'s own default. `write_new_pyramid` sets the same compressor explicitly (via a small `_pyramid_compressor(zarr_format)` helper), so removing the dependency doesn't silently change on-disk compression characteristics for real datasets, even though no test in this suite currently asserts on compressor choice.

**Alternatives considered**: have `write_new_pyramid` also call `add_half_pixel_translations` internally, with `from_images.py` simply not needing its own post-step — rejected specifically to avoid changing `tests/conftest.py`'s fixture metadata shape (see Rationale above); a smaller, more contained function beats a larger one that silently changes an unrelated caller's behavior.

## Decision: unify `downsample.py`'s two builder functions into one

**Decision**: `_build_new_coarser_levels` (previously `ngff_zarr`-based) and `_build_label_coarser_levels` (previously `label_downsample`-based) collapse into a single `_build_coarser_levels(zarr_path, num_levels, *, label: bool, downsample_func=...)`. The two were near-identical (~25 lines of shared group/metadata/coarsest-array setup) except for which one-line resample primitive ran per loop iteration; unifying picks the right function reference (`label_downsample` vs. the new `intensity_downsample`) once, up front.

**Rationale**: exact-duplicate scaffolding is the textbook case this codebase's own conventions already favor collapsing (constitution Principle I: "prefer editing existing modules over adding new abstractions... unused dependencies, dead code, and organizational-only indirection MUST be removed"); no new abstraction is introduced, just one fewer near-identical function. This also drops the `ngff_zarr` import from `downsample.py` entirely — its only other use in this codebase besides `migrate.py`.

**Alternatives considered**: keep the two functions separate for "clarity" — rejected; the two functions' only real difference (which resample primitive to call) is already expressed cleanly as a single ternary, and keeping them separate would mean two places to keep the shared scaffolding logic in sync going forward.

## Decision (context, not this feature's implementation): why not `ngff_zarr`'s own label-aware `Methods`?

**Context**: `ngff_zarr` publicly exposes a `Methods` enum including `Methods.ITKWASM_LABEL_IMAGE` and `Methods.DASK_IMAGE_MODE`/`DASK_IMAGE_NEAREST`, documented as appropriate "for label images" — `downsample`'s label path *could* in principle have been implemented as `nz.to_multiscales(image, method=Methods.ITKWASM_LABEL_IMAGE)` instead of a hand-rolled primitive.

**Rationale for not using it**: that API only operates on `ngff_zarr`'s own `NgffImage`/`to_multiscales` abstraction — a heavier dependency that `apply_mask` doesn't otherwise need at all (it never touches `ngff_zarr`). Since this feature's explicit goal is *one shared implementation* reused by `downsample`, `upsample`, **and** `apply_mask` (FR-003), a lightweight `dask`/`skimage`-based function that all three can call directly is the only design that satisfies that requirement; `ngff_zarr`'s built-in label method, however capable, doesn't fit the sharing requirement.

## Comparison context: how this codebase's resampling conventions now relate to `stack-to-chunk` and `nifti-zarr-py`

**Context** (informational, not a design decision — recorded here since it directly motivated exploring `ngff_zarr`'s `Methods` enum above): a prior investigation this session (cloning and reading both tools' source directly) found `ome-zarr-tools`' half-pixel-translation formula (`(scale_N - scale_0)/2`, anchoring level 0 at translation 0) matches `nifti-zarr-py`'s own "edge-aligned" default exactly, and diverges from `stack-to-chunk`'s convention (which gives level 0 itself a nonzero `+scale_0/2` translation). Binning-wise, `stack-to-chunk` defaults to plain local-mean `skimage.measure.block_reduce`; `nifti-zarr-py` defaults to `skimage.transform.pyramid_gaussian` (the same primitive this feature now uses as `ome-zarr-tools`' own default `downsample_func`) and — like this feature's `label_downsample` — auto-detects label/segmentation data and switches to a per-label-channel-probability-pyramid-plus-argmax technique. This feature closes the gap `ome-zarr-tools` previously had relative to `nifti-zarr-py`: `downsample` (not just `upsample`) is now label-aware.

## Post-implementation note: dask block size, sharding, and lazy label smoothing (branch `fix/pyramid-shard-sized-blocks`)

**Context**: converting a real 7526×6985×6985 float32 TIFF stack (`from_images --num_levels 8 --chunk_size 64 --target_version 0.5 --chunks_per_shard 16`) exposed problems in the pipeline this feature built. They were not caught by the test suite, whose fixtures are a few chunks per axis. The halo/overlap smoothing that replaced the plain `map_blocks` path described above came in separately (`2a28375`); the changes below build on it.

**Findings and changes**:

- **Dask chunks shrank below the Gaussian halo.** Each `intensity_downsample` call halves the dask chunks, and nothing rechunked between levels, so with 64³ chunks the input to level 6 was 2³ and `map_overlap` raised *"Overlap depth is larger than smallest chunksize"* (halo depth 3). `write_new_pyramid` and `downsample` now rechunk back to the working block shape before every level.
- **64³ dask blocks don't scale.** Using the zarr chunk shape as the dask block shape meant about 650M tasks for the stack above, and the job never got past single-threaded graph construction. Dask now works in one block per zarr shard (or per chunk when unsharded) at every level: about 449k tasks for the same stack. Each shard is written by exactly one task, avoiding partial read-modify-write of shards. This matches ome-zarr-py (`writer.py`: *"one dask chunk should correspond to 1 shard to prevent concurrent writes to 1 shard"*) and ngff-zarr (`to_ngff_zarr.py`: `arr.rechunk(shards)`). `from_images` no longer pre-rechunks to the chunk size.
- **`downsample`/`upsample` dropped sharding.** Both wrote new levels unsharded even from a sharded Zarr v3 dataset. New levels now keep the source level's shard shape, shrunk to fit small levels while staying a multiple of the chunk shape, via a new optional `NewLevel.shards` field (default `None`). `upsample` also rechunks after each level, since `nearest_upsample` doubles the dask blocks.
- **`upsample --smooth` loaded the whole level into memory.** It now uses `core.resample.label_smooth`: the same halo-aware per-block channel decomposition as `label_downsample`, without decimation. The result matches whole-array smoothing exactly, because a label absent from a block's halo has zero probability on that block's interior.

**Verification**: regression tests for each change, each failing on the pre-fix code. On real data, level 0 matched the source TIFFs on both sides of shard boundaries, and level 1 matched an unchunked Gaussian reference exactly on a crop across a shard seam.

**Known limitation**: building 1024³ shards from 2D slices keeps about one shard row of slices in memory (about 200 GB here), and dask reads ahead into later rows. The full run took 13.5 h and peaked at about 1 TB of memory, most of it spent in the kernel. A possible follow-up is to first copy the slices into a temporary z-slab zarr, as ngff-zarr's `to_multiscales` does for large inputs.
